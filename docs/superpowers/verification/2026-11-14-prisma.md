# Prisma implementation verification

Implemented on `codex/prisma-data-access`: four mapped public models, external
Auth references, initial SQL migration, server-only Prisma repositories,
transaction-local identity/RLS context, three APIs and three page loaders.
Supabase remains the database host and authentication provider.

## Verification performed

- Original baseline: 13 tests, lint and production build passed.
- Final ordinary suite: 109 tests passed, including route validation/auth,
  scoped data access, page fallbacks, lazy initialization and migration guards.
- Prisma validation/client generation succeeded offline.
- Standalone TypeScript checks, lint, production build and whitespace checks passed.
- Read-only live Supabase catalog query succeeded on PostgreSQL 17; checked the
  four application tables, policies, FK/check constraints, profile triggers and
  security-definer owner privilege context. No application rows were fetched.
- Independent review identified three migration/testing issues; fixed shared
  Supabase pooler identity, function ownership verification, and the integration
  test's insert-only feedback permission setup. No minor findings were deferred.

## Database acceptance still required

Actual Prisma-to-Supabase integration tests have NOT run. Two empty disposable
Supabase environments, their connection URLs, a test Auth service administrator
key and a disposable shadow database are required. The explicit integration
command currently stops for absent configuration; this is not a passing test run.

Full baseline equivalence against a freshly migrated reference, migration replay,
existing-data adoption, owner-change detection, real driver/RLS isolation and
permission/connection-reuse tests remain unverified. Live migration history,
application data, permissions and schema were not changed. Follow `prisma/README.md`
before deployment; client generation/build does not adopt the database.

## Decisions and tradeoffs

- npm/package-lock.json is canonical; retired yarn.lock to avoid diverging locks.
  Yarn users must use npm or regenerate their workflow.
- Installed Next 15.3.8 has no packaged guide directory; consulted official v15
  guides. Version-specific documentation differences remain a review consideration.
- Used a temporary npm cache because the user's default cache was not writable;
  this only costs temporary disk space.
- Generate migration SQL from history/model in an isolated shadow rather than
  introspecting the entire Supabase auth schema through migrate dev. This needs
  explicit review/deployment but avoids taking ownership of unmodeled Auth tables.
- A disposable plain PostgreSQL shadow gets explicit minimal Auth dependencies;
  keep this initializer aligned with profile-trigger requirements. Never reset a
  full Supabase project as a shadow.
- Added an explicit row generic to an existing Excel test for standalone typing;
  no spreadsheet behavior changed.
- Preserved existing policies/profile business rules and unrelated pre-existing
  security advisor findings. Existing hardening work remains separate.
- Reviewed package/version intent, not every generated transitive dependency
  change; full dependency security auditing is outside this migration.
